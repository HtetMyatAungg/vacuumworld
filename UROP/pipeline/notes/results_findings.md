# Results findings (evaluator run, 2026-07-01)

Based on `UROP/pipeline/results/large_llm_results/*.txt` and
`UROP/pipeline/results/small_llm_results/*.txt`, generated by `evaluator.py`
(`check_all` constraint report + `wall_f1_sweep([3..13])`).

## Zero-shot — universal collapse, model size doesn't matter

Every model, large and small, sits at F1=0.0 flat across N=3-13 and ~1/8
constraints passed. Large models fail via `existence_error` on undefined
`seen/1`/`grid_size/1`; small models are similar or worse (gemma3-4b averages
0.85/8). Zero-shot tells us nothing about abstraction vs hardcoding — it's a
floor effect where the models never produce queryable Prolog at all.

## One-shot (large models) — flat F1=1.0, but INVALID data

All 5 large models score a perfect flat 1.0 across N=3-13. This result is
contaminated: these `.pl` files were generated under the old one-shot prompt
that leaked the fully parametrised wall rule directly into the worked
example (see `LLM_multi_harness.py` / `smallLLM.py` one_shot_prompt — since
fixed to stop the example before Section B). A model copying that template
is indistinguishable from a model abstracting it, so this ceiling result
cannot be used as abstraction evidence.

**Action: regenerate one-shot samples for all large models under the fixed
prompt, then re-run evaluator.py, before this condition goes in the report.**

## One-shot (small models) — same contamination, but a hint of signal

gemma3-4b: 0.03 at N=3 decaying to 0.0 by higher N. qwen2.5-3b: 0.01 at N=3
to 0.0. Near-total failure overall (avg ~1.8/8 constraints), but this is the
only condition besides schema-based-small with any N-dependent decline
rather than a flat 0 or flat 1. Same prompt-leak caveat applies — regenerate
before drawing conclusions.

## Schema-based (large models) — mostly flat ceiling, one exception

- claude-sonnet-4.6, gemini-2.5-flash, gemini-3.1-flash-lite: flat F1=1.0.
- gemma-4-31b: flat but offset at 0.93 (looks like a fixed bug, not
  N-dependent).
- deepseek-2.5-flash: 0.83 (N=3-7) -> 0.79 (N=9-13) — a mild, not fully
  monotonic decline.

This condition was not affected by the one-shot prompt leak, so it's
trustworthy data, and it's still mostly abstraction-consistent.

## Schema-based (small models) — the most interesting result so far

qwen2.5-3b is flat at F1=0.0 (total failure — also where we caught the
infinite-recursion timeout in `qwen2.5-3b/schema-based/schema_based_sample_9.pl`,
see below). **gemma3-4b shows a real decay curve:**

| N  | F1    |
|----|-------|
| 3  | 0.243 |
| 4  | 0.233 |
| 5  | 0.244 |
| 6  | 0.206 |
| 7  | 0.200 |
| 8  | 0.212 |
| 9  | 0.227 |
| 10 | 0.148 |
| 11 | 0.139 |
| 12 | 0.131 |
| 13 | 0.124 |

Roughly flat ~0.2-0.24 through N=3-9, then a genuine step-down to ~0.12-0.15
from N=10 onward. Overall competence is low (avg 2.1/8 constraints), so this
isn't the clean "near-perfect near the demonstrated N, decaying elsewhere"
textbook shape — but it is the only condition in the entire dataset, across
both model classes and all three prompt types, that shows a real N-dependent
downward trend rather than flat-zero or flat-ceiling. It's the closest thing
to evidence for the hardcoding side of the research question, and it shows
up specifically in a small model under schema-based prompting.

## Known failure modes found during this analysis

- **gemma3:4b "comment everything out" (zero-shot sample 3):** model emits
  a file that is almost entirely Prolog comments plus one inert
  `grid_size(N).` fact. Trivially passes syntactic validation (nothing to
  throw a syntax error) despite containing no real logic. Syntactic-only
  validation can't distinguish "correct" from "empty" — semantic/F1 layer is
  what actually catches this. See `UROP/pipeline/notes/first.md`.

- **qwen2.5-3b infinite recursion (schema-based sample 9):**
  `seen(agent(_,loc(X,Y),_)) :- seen(agent(_,loc(X,Y), _)).` — the clause
  body is structurally identical to its own head with no base case, so
  calling it never terminates. This hung `evaluator.py`'s subprocess calls
  indefinitely until a `timeout=10` was added to `run_swipl()` in
  `evaluator.py`. At least 2 such timeouts were caught across the small-model
  one-shot/schema-based runs.
